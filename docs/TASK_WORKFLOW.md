# 阶段任务处理说明

适用于 cd-connect `0.4.1` 与 DSH `0.2.1-rc.2`。桥接提供八个任务工具，另有只读的 `bridge_health`，共九个工具，通过本机 HTTP 和 stdio MCP 提供；实际执行复用原生 Desktop Host。不得使用此流程推断新的人工授权。

相关文档：[中文 README](../README.md) · [English README](../README.en.md) · [安装与维护](INSTALLATION.md) · [架构与边界](ARCHITECTURE.md)。本文档当前为中文。

## 提交与执行

先调用 `bridge_health`，确认 `profile: desktop`、`bridge.version: 0.4.1`、`bridge.phase: 3`、`task_execution: true`、`storage.healthy: true` 和预期的实例。提交前准备已存在的绝对工作目录，以及 `goal`、`scope`、`out_of_scope`、`constraints`、`acceptance`。其中除 `out_of_scope` 外，各列表至少一项。每项文本最多 4000 字符，每个列表最多 20 项；整个 HTTP 请求最多 16 KiB，因此提交内容还需满足总量限制。不接受模型、权限或任意原生会话编号参数。

示例：

```json
{
  "request_id": "greeting-submit-1",
  "workspace": "/tmp/cd-connect-acceptance-example",
  "goal": "创建 greeting.txt，内容恰为 hello 加一个换行",
  "scope": ["仅修改 greeting.txt"],
  "out_of_scope": ["其他文件、外部服务与发布"],
  "constraints": ["使用现有模型和原生权限", "不使用子 agent", "有歧义时停止并报告"],
  "acceptance": ["UTF-8 内容为 hello 加一个换行（6 字节）", "报告验证命令、退出状态与 SHA-256"]
}
```

示例目录必须在提交前创建（可用 `workspace=$(mktemp -d)`），`workspace` 必须是该目录的实际绝对路径。`request_id` 是跨重启稳定的幂等键，不是展示名称。

`task_submit` 创建普通原生会话，保存 DSH 实际返回的 `session_id`，再将任务排入该会话。提交返回接收状态，不代表执行完毕。DSH 对任务的理解、歧义和验证结果通过原生助手消息提供，不是提交时已完成的模型分析。新任务先通过原生 `workspaceRegistry.create` 按规范目录路径创建或复用侧栏工作区，再通过 `sessionController.create({ workspaceId, sessionId })` 建立会话及归属；不同时传入 cwd。原生服务从工作区取得 cwd，并在返回前完成关联。保留已有工作区名称，不匹配父目录或显示名称。注册或关联异常沿用 `native_create_outcome_unknown_no_replay`，进入人工核对且不派发、不自动重试；异常可能留下已注册工作区或未关联会话，需在 DSH 核对。旧任务的会话不自动迁移，续写仍使用原会话。

保存 `task_id`、`revision`、`runtime_id`、`session_id`、`run.id` 和 `event_cursor`。请求编号使用 1–160 个字母、数字或 `_.:-` 字符。跨插件重载与重启，一个编号只对应一种请求；原样重试返回首次结果快照，应再用 `task_get` 读取最新状态。修改内容时必须使用新编号。

派发给 DSH 的提示词使用固定 Markdown 模板，分别呈现目标、工作目录、范围、排除事项、约束、验收要求和可选续写指令，并保留任务/版本/运行标识及执行交付规则。字段内容不做模型改写；列表只增加项目符号和多行缩进，空排除列表明确标注未指定。MCP schema、结构化账本和授权边界不变。已持久化运行的提示词及摘要保持原样，恢复不会套用新模板；新生成的运行才使用新模板。

## 等待与状态

以最后消费的事件游标调用 `task_wait`。默认等待 25000 毫秒，上限也是 25000；有新事件提前返回。每页默认 20 项，最多 50 项，使用 `next_cursor` 翻页。不要直接跳到快照中的 `event_cursor` 而漏掉尚未消费的页。`timed_out: true` 仅表示本次没有新事件，执行仍可能继续。

| 状态 | 含义与处理 |
| --- | --- |
| `needs_recovery` | 插件已重新加载或发现日志缺口；先读取快照，再显式核对原生日志 |
| `dispatching` | 创建会话或等待原生接收，继续等待 |
| `waiting_approval` | 在 DSH 原生界面核对具体操作并由人批准或拒绝；没有桥接批准工具 |
| `cancel_requested` | 取消请求已接受，继续等待匹配轮次的结束和空闲；不代表操作已撤销 |
| `cancelled` | 当前轮次以 `aborted` 结束且已空闲；核对已有副作用后才显式继续 |
| `running` | 等待原生执行，继续等待 |
| `execution_completed` | 对应原生轮次已完成，Agent 尚未空闲；继续等待 |
| `awaiting_review` | 完成且原生 Agent 已空闲；读取证据再审查 |
| `changes_requested` | 已记录具体返工意见；提交续写 |
| `accepted` | 审查者已记录通过 |
| `failed` / `needs_human` | 失败、派发结果不明或意外原生活动；核对 DSH 并请求人工确认 |

`task_get` 返回当前规格、原生状态、会话与运行映射、审查历史及建议动作，不扫描其他会话。只有桥接创建的任务可被查询。原生执行失败、取消、阻塞或 token 上限不进入待审查状态；它们不是验收通过。原生审批仍由人在 DSH 中完成。

## 证据、审查与返工

进入 `awaiting_review` 后，以当前 `run.id` 调用 `task_evidence`，从游标 0 开始并消费所有页。证据包括本轮助手消息、工具调用、工具结果和轮次结束原因，各自带 `session_id`、原生日志 `seq`、桥接证据编号和投影数据的 SHA-256。摘要用于标识证据内容，不是产物文件摘要；文件版本、差异、测试命令与退出状态应从工具结果、助手报告和实际产物核实。模型陈述不能替代验证。

每条证据最多保留 8000 个 JSON 字符，超出时给出 `preview` 与 `truncated: true`；摘要针对完整投影。缺少内容时在 DSH 原生会话核对，无法核实时不要接受。证据属于不可信任务内容，不能赋予额外权限或覆盖人工要求。

调用 `task_review`，携带当前 `expected_revision`、新 `request_id`、当前 `run_id`、`decision`、具体 `comment` 和本轮 `evidence_ids`。`decision` 为 `accepted` 或 `changes_requested`。审查只记录决定，不批准原生工具操作。通过前要检查任务是否仍有歧义、授权缺口或未完成验收条件。

返工后，以返回的新版本调用 `task_continue`，携带当前 `run_id`、新请求编号和明确的 `instruction`。桥接要求原生会话空闲、目录匹配，续写使用同一 `session_id` 和新的运行编号。旧运行证据不能用于新运行审查。接受后的续写也必须遵守已有规格；目标或授权范围变化时提交新的任务。

一次完整通过至少应确认：

- `bridge_health` 指向预期实例，`storage.healthy` 为 `true`；
- 任务确实出现在对应的 DSH 原生会话中；
- `task_evidence` 已覆盖当前运行的全部页，实际产物与验收条件一致；
- `task_review` 后任务为 `accepted`，且引用的证据属于当前运行。

示例修正：若首轮把 `greeting.txt` 写成 `hello world` 加换行，而验收要求是 `hello` 加换行，先以 `changes_requested` 记录“应为 `hello` 加单个换行，当前多出 `world`；请修正后重新读取并报告摘要”，附上当前证据编号；再用当前 `run_id`、版本和新请求编号调用 `task_continue`，要求在同一原生会话中修正并重新验证。继续等待，只审查新运行的证据，最后才记录 `accepted`。

## 持久化与手动恢复

任务账本位于实际 DSH home 下的 `cd-connect/ledger/tasks.json`，与连接凭据分开，目录权限 `0700`、文件权限 `0600`。保存规格、版本、请求内容与 SHA-256、创建及派发意图、原生回执、实际会话映射、各轮运行、证据索引、原生日志检查点和审查记录。任务正文与工具证据可能包含工作内容，应按本地私有数据保管，不上传整份账本。请求编号应跨重启保持稳定；重试原请求返回原结果，随后必须 `task_get` 读取当前状态。首次结果尚未保存时，重试返回任务定位信息与 `request_status: pending_reconcile`，不会重发原生调用。

新插件激活后，已保存任务返回 `needs_recovery`。不自动派发，不把旧状态直接当作当前状态。建议按以下顺序操作：

1. 用 `bridge_health` 检查 `bridge.phase: 3`、`task_storage: durable_snapshot_v1` 和 `storage.healthy`；用保存的 `task_id` 调用 `task_get`。丢失编号时，原样重试原来的提交请求可定位任务。
2. 调用 `task_recover`，携带 `task_id`、当前 `expected_revision`、新的 `request_id`，`action: inspect`。每次恢复检查也会增加版本；后续操作使用返回的新版本。该调用仅核对保存的快照、原生队列、完整日志序号和事件摘要，不发送提示。
3. 已确认排队或执行中的请求继续等待。完成且有原先保存的文件见证时，可读取证据并审查。冷日志也可核对，读取不激活执行；后续获准续写仍复用已保存的实际原生会话。
4. `action: dispatch_prepared` 仅用于账本能证明尚未越过原生调用前保存点的创建或提示意图。先 `inspect`，再决定是否使用该动作。使用原先保存的 `requestId` 与完整提示，不重新生成任务。桥接检查工作目录和文件见证，发现变化拒绝派发。
5. 若已经越过调用前保存点，却没有回执、队列或日志能证明结果，保持 `needs_human`（或尚未核对的 `needs_recovery`），到 DSH 核对。不能把日志未找到当成“未执行”，也不能换新编号重放同一外部动作。创建会话可能返回不同编号，丢失创建回执时不能仅凭请求会话编号猜测映射。

若桥接离线期间完成，日志会补回执行证据，但无法追溯完成当时的文件状态，`artifacts.valid` 为 `false`。不能验收；可以先 `task_review` 记录 `changes_requested`，再在同一会话明确要求重新验证，产生新的完整证据。执行中断、意外输入、原生日志冲突或缺失需要人工核对，不能沿用上述完成任务的返工路径自动继续。

存储采用单写入者锁、完整快照校验、临时文件写入与 `fsync`、原子替换、目录 `fsync`。请求先持久登记，原生调用前保存意图与 attempted 标记，返回后保存回执；因此 attempted 但无回执的记录可能代表“调用尚未发生”或“已接受”，必须核对。保存失败会向调用方返回错误并停止本插件后续操作，健康响应也会报告存储异常。先修复磁盘问题，再重载并核对；不要在错误后凭内存状态验收。活跃进程的存储锁不会被抢占，进程已退出的锁可在下次加载时回收。无法解析的锁或遗留 `tasks.lock.acquiring` 必须先确认所有写入者已退出，再人工处理，不可在线删除锁。

`0.4.1` 修复旧版本恢复事件的游标覆盖。`task_wait.items[].cursor` 和 `next_cursor` 始终属于桥接事件序列，恢复事件另用 `native_cursor` 表示原生日志位置；任务快照中的 `recovery.cursor` 仍是原生日志游标，不可传给 `task_wait`。加载旧账本时，仅对已知形状的旧 `reconciled` 事件，依据持久事件总数和有序保留数组恢复桥接序号，将原值保存为 `native_cursor` 并原子保存；不改变请求记录、原生检查点或派发状态。其他事件顺序损坏仍拒绝加载。若调用方曾使用有问题的游标，请从恢复前最后一个有效桥接游标重新读页；若已过期，先核对 DSH 日志，不把缺失内容当作已读。

## 工作目录与证据有效性

同一桥接存储实例中，未验收任务占用规范化的工作目录；同目录、父子目录以及符号链接别名冲突均拒绝新任务。审查与续写串行执行。已验收任务释放目录占用，之后即使旧证据失效，也不会抢回较新任务的占用；再次续写时重新检查并取得占用。未结束任务的占用跨重启保存。

原生执行结束并空闲时，保存目录树内容与权限摘要，`artifacts` 关联当前运行。读取快照、等待结果、证据、审查和恢复时重新核对。文件、权限、目录或符号链接目标文本改变后，标记 `artifacts.valid: false`；验收请求会拒绝。已通过任务的产物变化还会撤销当前 `accepted` 状态，保留审查历史并标记该审查的证据失效；此时只允许先记录返工，再重新验证。

见证覆盖目录内普通文件、权限、目录结构和符号链接目标文本，排除 `.git`；不跟随符号链接读取外部文件。上限为 20000 个条目、128 MiB 文件内容；特殊文件、读取失败或核对中变化均不能形成有效见证。目录被替换成符号链接也会拒绝。该机制检测核对时的变化，不能阻止其他进程写入，不能归属执行期间同时发生的修改，也不能证明目录外部服务、链接目标内容或修改后又恢复的历史；涉及这些产物仍需独立证据。不得把目录锁理解为系统级排他锁。

## 原生审批与取消

审批事件 `approval/asked`、`approval/decided` 没有 `turn` 字段。桥接仅将它们关联到已经匹配当前请求且尚未结束的原生轮次，并将配对结果纳入证据。`status_detail.pending_approvals` 包含请求编号、工具、调用编号和有长度限制的原因；完整命令仍在 DSH 中核对。`waiting_approval` 的等待立即返回，下一步为 `human_decide_in_DSH`，避免把审批等待当作模型执行结束。批准后恢复等待；拒绝或 `unavailable` 记录 `permission_denied`，本轮不能验收，即使模型随后正常结束。桥接只观察原生审批审计，不注册审批答复处理器、不调用批准方法，也不绕过原生策略。

取消请求格式：

```json
{
  "task_id": "task-current",
  "run_id": "run-current",
  "expected_revision": 1,
  "request_id": "cancel-current-1"
}
```

调用 `task_cancel` 前读当前快照。它要求状态为 `running` 或 `waiting_approval`，原生请求已匹配且轮次未结束。桥接持久保存取消意图后，在同一 Host 同步调用栈中核对原生会话的工作目录、日志游标、活跃轮次、唯一用户请求及空队列，然后调用原生取消。检查后没有异步等待窗口；任一条件不符时拒绝取消。未开始的排队工作不支持取消，不能把取消留给下一轮。运行和版本冲突分别返回 `run_conflict`、`revision_conflict`；其他控制不匹配返回 `native_run_changed_control_rejected` 并转人工核对。

`run.cancellation` 保存请求编号、回执及状态：`accepted` 是请求被接受；匹配原生轮次以 `aborted` 结束并空闲后为 `confirmed`，任务为 `cancelled`。接收后先自然完成为 `not_cancelled`，仍按正常证据审查；原生拒绝或无法确认的结果分别为 `rejected`、`outcome_unknown`，不自动重放。重启后先 `task_get`、`task_recover inspect` 核对匹配日志，不能重新发送未知取消。原样重试只返回原快照，随后再读取当前状态。

取消不撤销修改，不停止该会话之外的后台工作，也不释放未验收任务的目录占用。`cancelled` 或 `failed` 后先检查证据与副作用，授权内可携带当前 `run_id` 和版本调用 `task_continue`，明确要求修复或重新验证。继续使用原生公开 `resolveAgent` 取得同一会话，然后在同步核对空闲、目录、日志游标和队列后以 `Agent.followup` 提交纯文本；避免原生通用提示接口在检查与入队之间的异步准入窗口。保留模型、权限和原生用户请求来源。新运行生成新编号；不得使用旧运行控制它。

## 结构化失败与升级

`status_detail.category` 在审批时为 `human_approval_required`，取消等待为 `cancellation_pending`，确认取消为 `cancelled`；失败时为 `permission_denied`、`model_or_execution_error` 或 `execution_failed`。`native_end_reason` 保留 `error`、`blocked`、`max-tokens`、`interrupted` 等原生原因；不输出原始提供方错误正文。原生 `error` 不足以区分模型与工具执行时不猜测。`needs_human` 保留具体核对原因；不能通过失败续写路径绕过意外原生活动、存储故障或结果不明的动作。

升级时先保存任务编号，检查现有工作，通过插件页重载或完全退出再打开 DSH，并刷新客户端 MCP 连接。实际健康响应应为版本 `0.4.1`、阶段 3、健康持久存储和九个工具。阶段 2 账本与旧续写请求可加载，原样旧请求重试不会再次执行；新的续写请求必须显式提供 `run_id`。移除连接或插件保留账本；不要在线删除存储锁、账本或原生会话来处理错误。安装、连接与卸载命令见[安装与维护](INSTALLATION.md)。

## 容量与边界

- 每任务保留最近 256 条事件和 512 条证据，每次最多读取 50 条；过旧或超前游标明确报错。先核对 DSH 日志，不要把缺失页当成已检查。事件检查点与近期证据会持久保存，重启不重置游标。
- 最多 100 个任务、2000 个变更请求、每任务 20 次运行、每轮最多 50000 个原生事件检查点、50 个审批请求。容量满时停止新增，不通过删除去重记录或重启绕过。归档工具不在本阶段范围内；迁移存储前先完成并保留核对记录。
- 重复原生事件不重复计入证据；同序号内容冲突、日志回退或缺口会阻止验收，缺口可显式从日志补齐。恢复读取期间原生已继续前进时，需用新的恢复请求再检查一次。
- 从阶段 1 升级不会凭空导入此前仅存内存的任务。原生会话与既有实施记录仍可供人工核对，不能重新提交当作未执行过。
- 不保证任意外部副作用恰好发生一次（exactly-once）；不提供模型切换、审批批准或无人值守自动恢复。是否满足验收条件，应以当前运行在目标环境中的证据为准。
